# ADR 0005: Negotiated task-state authority for plugin composition

Status: Accepted design for Issue #13, after resolving the seven-finding pre-implementation audit. This decision authorizes implementation against the updated Spec; it is not an implementation, independent review, or release PASS.

## Context

The Connector's durable ACK proves consumption, including no-effect rejection. Neither an offer nor an ACK carries authoritative job revision or mode. Task 5's approval reservation and cancellation owner require those facts, and Agent creation must not treat an acknowledged rejected claim as permission. Current business revision rejection can also leave an allocated client sequence permanently unconsumed. These are integration gaps in the approved Task 6, not grounds to weaken receipt, approval or exactly-once limitations.

## Capability and transport

Keep envelope version1.0. Add opt-in job-coordination-v1 alongside durable-receipts-v1. Legacy peers receive their existing shapes and semantics. The composed plugin requires both echoes before recovering pending commands, then a fresh state exchange in the current socket epoch before starting work or emitting the extended ADR0004 event projection. Replayed welcome metadata is receipt evidence, not proof of the current server executable's support after rollback. An old pinned hello without the requested capability is an explicit incompatible-state condition; retain its identity and durable database, without silently opting it in or promising an unimplemented drain migration.

The client adds job.sync, strict payload {job_id,attempt,nonce}. Each live sync allocates a new nonce, message_id and correlation_id, stores them before send and never recycles them after timeout/loss. The server adds job.state, strict payload with job_id, repository_id, mode, requested_attempt, current_attempt, status, job_revision, cancel_revision, lease_id, lease_expires_at, expires_at, observed_at, state_valid_until, request_message_id, request_sequence and nonce. Mode is normal/read_only; status uses the existing JobStatus enum. UUID/repository/calendar validators apply. Requested attempt is positive, actual attempt/revision nonnegative, all within their PostgreSQL integer limits; checked increments must not overflow. cancel_revision is null or a nonnegative transition revision no greater than job_revision. Lease fields are null together. No raw request, path, Harness identity, credential or action content is returned.

For a new authorized sync, lock job before connector, enforce exact current owner/connector binding and capability, consume the next client sequence, read actual DB clock and row state, and persist job.state plus its ordinary receipt ACK in one transaction. Sync does not alter job status/revision, renew the offer or job, or execute anything. It is sequenced after all previously allocated client business writes, proving observation after their consumption, not after their success. requested_attempt echoes the request while current_attempt is the actual row value, so a mismatch can be reconciled without fabricating an active attempt. Initial mode is established here and persisted with the local intent; it is not assumed from the offer.

job.state is a business response, never receipt evidence by itself. Do not acknowledge a client row or advance a prefix from it. Keep the established original-response plus receipt-ACK metadata pattern, immutable negotiated receipt profile and ordinary ACK prefix validation. Duplicate sync restores the original state and its recorded ACK without rereading the job. Preserve payload observed_at and state_valid_until forever; only the outer receipt-delivery envelope may refresh under negotiated tombstone rules. An expired snapshot can be consumed for replay but cannot become live authority. Exact original request binding must survive tombstones and reconnect; sequence gaps, fabricated replacements, unavailable DB state and unknown response types still fail closed. Gateway ordering, batch limits and window bounds remain in force.

## Freshness and operational authority

The server fixes state_valid_until at observed_at plus2seconds. This is a snapshot admission boundary, distinct from job expires_at and outer delivery expiry. The client stores monotonic enqueue time and an absolute2second waiter deadline, with at most32 waiters and one perjob. It registers the waiter before scheduling send. Timeout does not remove or renumber its durable sync; it ends only that live admission. Persisted inbound replay has no original live epoch and must never resolve a new waiter. Every actual socket close/error/supersession/shutdown aborts the old epoch before callbacks can grant authority; reconnect creates a new epoch, never revives the old one.

At response/admission, require exact pending request identity/correlation/nonce, actual delivering socket epoch, expected local job/repository/attempt and original validity. Track monotonic elapsed time and fail admissions closed when the wall-minus-monotonic offset changes by more than1second. DB observed_at must fit the local send/receive interval within1second skew. For applicable remote lifetimes, subtract the complete monotonic elapsed request time and1second skew allowance from remote remaining lifetime at observed_at; this deliberately never refunds network delay. Recheck before the first side effect, not only on parsing.

After a valid immediate admission, an operation's lifetime uses its own immutable business deadline and epoch/ownership signals, not a renewed snapshot. Snapshot expiry does not by itself turn an already admitted successful cancellation drain into a second cancellation; conversely it cannot admit a new effect. Approval wire expiry is an absolute timestamp clamped to remote job expiry and configured timeout. Its local currentness also has an independent conservative monotonic deadline; no monotonic time is serialized and wall-clock rollback cannot extend a grant. A later approval always obtains a new snapshot/reservation. Server CAS remains authoritative for remote changes after observation; a snapshot is not a distributed lock.

## Claim, approval and cancellation

Persist one offer/attempt/lease intent and preallocated SessionId locally before factory creation. After claim consumption, a fresh state must prove running, exact offered attempt/lease, configured repository, server mode and unexpired initial-start lease/job. Only then may the locally CAS-owned intent create its Agent and issue the initial request. A consumed claim rejection cannot meet this check. Recovery of a previously started attempt may outlive the30second dispatch lease, but must use the same persisted SessionId and current job/attempt authority. Missing durable session or ambiguous initial-request history is HARNESS_SESSION_LOST/unavailable, never a second execution with a new ID.

Acquire the per-job publication/admission barrier BEFORE allocating approval's sync. Previously allocated business writes precede it; no progress may allocate between sync, revision R+1 reservation and durable approval enqueue. Buffer ordinary redacted progress for the full pending-approval lifetime, bounded32events/16KiB aggregate perattempt. Overflow revokes and follows a fixed failure/unavailable path, not silent dropping or unbounded buffering. Terminal and cancel revoke synchronously and use their distinct arbitration path. Only the exact owner/canonical action and existing local classifier may reserve. Decisions bind original approval revision/fingerprint/lifetime and never override denied. Release does not undo consumed revision, and reconnect cannot revive an ended approval.

Persist jobs.cancel_revision only in the server transaction entering cancelling, at that transition's new revision. Ordinary progress may increase job_revision without changing this provenance. Expose both. The cancel command must match confirmed cancel_revision for the same current cancelling attempt before supplying the stable CancellationOwner; later ordinary revision growth is not a new cancellation. Terminal state wins. Do not derive cancellation provenance from event source labels that Connector input can imitate.

The additive migration adds a nullable integer cancel_revision with a check that a supplied value is nonnegative and no greater than revision. It does not backfill legacy rows. Legacy cancelling rows without this provenance are explicitly unavailable for new-profile cancellation admission, even if an event source string or unverified old command suggests a revision. No implicit repair or queue deletion is authorized. Future proof-based repair would need a separate reviewed migration; it is not part of this rollout. New server cancellation writes the transition revision atomically with its command. Old application versions ignore the added column; rollback retains the column and values. Migration tests must prove that old rows remain null, invalid values fail, new transitions populate the value, later progress preserves it, and rollback-compatible reads still work. The cost is conservative unavailability for legacy cancellation reconciliation, not invented authority.

## Consumed conflict dispositions

Under this profile only, schema-valid operations for a currently authenticated job binding that encounter enumerated status/attempt/revision conflicts may be consumed with a fixed no-effect rejection plus ordinary ACK. Use a dedicated business-conflict outcome at those precise checks and roll back all savepoint effects; do not broadly consume ConnectorStoreError, database failures or unexpected exceptions. Unknown/forged claim lease provenance remains a hard rejection. This lets a legitimate stale approval request be followed by a new sync rather than poisoning every later sequence.

A sync for a formerly bound job can receive consumed JOB_AUTHORITY_UNAVAILABLE only with validated durable server-authored original-offer/claim proof of the old owner/connector/job binding. It reveals no new binding's state and has no job mutation. Missing/cross-owner/unproven requests, malformed identity and unavailable storage remain explicit hard failures. A later sync cannot bypass their unconsumed frame; surface the real unavailable/recovery condition instead of an endless retry promise. Historical exact duplicate responses restore only the authorized original disposition and never create a live waiter or reread the reassigned job.

## Required evidence and rollback

Use actual PostgreSQL and loopback TLS/SQLite tests for: capable and legacy negotiation; old pinned hello and rolled-back server; claim ACK with business rejection; fresh claim acceptance; mode/attempt/lease mismatch; stale R approval after remote revision change followed by successful next sync; missing/forged/cross-owner/historical binding; immutable duplicate state after DB mutation, expiry and tombstone; state-only delivery without receipt retirement; ACK-before-waiter-loss replay; disconnection after persistence and before callback; synced cancel with later progress revision; legacy null-provenance migration and refusal to infer from ambiguous data; overflow/clock skew/wall discontinuity; per-job publication race and buffer overflow; actual ordered restart with no duplicate Agent work.

Both endpoints ship together in v0.2.0 after the whole Issue13 gate, not this ADR alone. Retain durable queued data during rollback and mark incompatible composition unavailable. Never downgrade to ACK-as-permission, alter protected main/CI, erase queues to clear a sequence or claim fake-Harness tests prove real-loop/device acceptance.

## Exact schema and staged implementation boundaries

The shared protocol exports JOB_COORDINATION_CAPABILITY = job-coordination-v1, JobSyncPayloadSchema, JobStatePayloadSchema, JobSyncPayload and JobStatePayload. Both payload objects are strict; no coercion, defaults or optional fields. UUID fields are job_id, nonce, request_message_id and nonnull lease_id, using the existing UUID normalization. repository_id uses RepositoryIdSchema. mode is the exact normal/read_only enum and status is JobStatusSchema. Requested attempt (job.sync.attempt and job.state.requested_attempt) is integer1..2147483647; current_attempt and job_revision are integer0..2147483647. cancel_revision is required nullable integer0..2147483647 and, when supplied, no greater than job_revision. request_sequence uses the existing positive safe-integer sequence domain, not the PostgreSQL job revision limit. lease_id and lease_expires_at are required nullable fields, either both null or both nonnull. expires_at, observed_at and state_valid_until are required RFC3339 calendar-valid strings; lease_expires_at is one when nonnull. State validity is exactly2seconds after observation, comparing instants with the shared precision-preserving timestamp primitives rather than truncating sub-millisecond fractions through Date.parse. Different timezone spellings and trailing-zero fractions of the same instant are equivalent. Reconciliation permits expired job/lease times, different requested/current attempts and null cancellation provenance; local admission enforces the applicable authority conditions.

A first independently testable slice may add only these payload exports and tests without registering new message types in the legacy envelope unions or advertising the capability from a live endpoint. Subsequent server/transport integration adds the actual envelopes and negotiation together with their handlers. The plugin must remain unavailable until that integration and the fresh-state gate are complete. Exported schemas alone cannot complete Issue #13 or enable a release.

## Local deadline adapter contract

At sync allocation capture wall w0 and monotonic m0; at admission capture w1 and m1. Require finite values, 0 <= m1-m0 <2000ms, absolute change in wall-minus-monotonic offset <=1000ms, observation inside [w0-1000ms,w1+1000ms], and a strictly positive snapshot remaining lifetime. For each applicable remote deadline D, conservative remaining lifetime is D-observed_at-(m1-m0)-1000ms; never reset m0 on send/replay. The snapshot check uses D=state_valid_until. Initial start additionally uses both lease_expires_at and job expires_at; previously started recovery and approval use the job deadline, not the dispatch lease.

For an approval admitted at m1/w1, compute local monotonic deadline as m1 plus the lesser of configured approval lifetime and the conservative remaining job lifetime. Keep ApprovalReservation.deadline as an absolute Unix-millisecond wire deadline, capped by job expires_at and w1 plus configured lifetime. ApprovalReservation.isCurrent and its signal independently enforce the original monotonic deadline, epoch, owner/action identity and clock-discontinuity policy even after bookkeeping release. A wire-clock rollback can never extend local permission; no monotonic reading is serialized as an RFC3339 time. New snapshot acquisition requires a new nonce and deadline. Inject paired clocks in coordinator tests; the production clock uses Date.now and performance.now. The bridge must not await state or Agent completion inside the transport's serialized onCommand intake callback.

## Exact no-effect conflict categories

The new profile can consume only explicit classified checks after authenticated current binding: approval.requested with a no-longer-approvable status, wrong attempt, or requested revision different from checked R+1; job.event with wrong attempt, ordinary progress after terminal, an unclaimed current state, or a disallowed status transition; job.cancelled with wrong attempt or a nonterminal state other than cancelling. An exhausted 32-bit job revision/attempt cannot increment and yields a fixed no-effect business-limit disposition at its explicit check. Existing safe terminal-repeat behavior remains unchanged. A job.claim status/attempt conflict is consumable only when validated server-authored original-offer identity proves that exact job, connector, lease and offered attempt; mismatching or unavailable lease proof stays hard denied. Existing authorized business-deadline rejection behavior remains in force.

Split combined missing-job and stale-business checks: absence or cross-binding is not a business conflict. Unexpected zero-row writes under held locks, sanitization failures, uniqueness errors, malformed payloads, unknown message types, database failures and replay/sequence inconsistencies are not converted by these categories. A dedicated internal disposition, not shared public error-code equality, controls savepoint rollback and receipt creation. Persist the original negotiated profile and fixed rejection response with its ordinary ACK. Historical new sync no-authority consumption requires the separate validated prior-binding proof already specified above; it never returns another binding's state.
