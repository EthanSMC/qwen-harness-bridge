## Manual macOS acceptance — NOT EXECUTED

The plan for this task requires exercising install, credential rotation, and rollback on a test Mac account: adding the bootstrap credential to the Keychain, configuring one repository alias, loading the extension, verifying the outbound connection, rotating the credential without losing jobs, stopping Harness, installing the previous plugin artifact, and reconnecting with the same SQLite mapping. **No macOS host was available, so none of these steps is claimed as evidence**, and this document records no Harness version and no macOS version because none was exercised.

The procedure, including its verification checkpoints and failure handling, is written up in:

- `docs/runbooks/install-harness-plugin.md`
- `docs/runbooks/rotate-connector-credential.md`
- `docs/runbooks/rollback-harness-plugin.md`

The plan's expected manual result is likewise **NOT EXECUTED**: submit from the MCP fixture, an online Mac claims within five seconds, a safe repository task completes, approval pauses and resumes exactly once, reconnect does not duplicate work, and the final cloud output contains no raw secrets or full logs.

## Known limitations

- Exactly one configured repository root is supported; more than one aborts startup with `MULTI_REPOSITORY_UNSUPPORTED` before any effect is registered.
- The packaged artifact ships self-contained source maps (`inlineSources`), which increases its size.
- The plugin package version remains `0.1.0`; synchronized SemVer, the tag, and the GitHub Release are release-process actions.
- `pnpm -r typecheck` could not run on the authoring host because the recursive script resolves a store-linked `pnpm` CLI that is missing there (`MODULE_NOT_FOUND`); per-package `tsc --noEmit` was used instead, and CI runs the supported command.
