## Self-contained packaging strategy (the Issue #8 gate)

The Issue authorises either bundling the protocol runtime into the plugin artifact or publishing an exact compatible `@qhb/protocol` artifact first. This change implements the bundling option as a vendored runtime closure:

- `packages/harness-plugin/scripts/package.mjs` resolves the plugin's runtime dependency closure, skipping every `@deepseek-ai/*` host peer, and copies it into `package/node_modules/**` inside the archive. The private workspace package `@qhb/protocol` is copied as an ordinary package.
- The packaged manifest drops `workspace:` specifiers, lists the vendored packages in `qhbVendoredDependencies`, and pins the shipped schema with `qhbSchemaSha256`. `devDependencies` and repository-only `scripts` are removed from the packaged manifest.
- Vendored packages keep their published `files` selection, their `package.json`, and any native build output; vendored test material and C/C++ build sources are pruned because a runtime never loads them.
- The smoke test installs the archive into a clean temporary root **outside the repository tree** (no monorepo `node_modules` and no Git repository in its ancestry), links only the seven `@deepseek-ai/*` host peers, and imports the packaged entry from a separate process.
- The negative control extracts the same archive minus `package/node_modules/@qhb/protocol` and asserts that the same import fails with `Cannot find package '@qhb/protocol'`. The archive is therefore proven to carry the runtime rather than resolve it.

With the resident host up and a job in flight against a deliberately slow stub model, the host process was killed and restarted with the same profile and journal:

| Observation | Exact value |

| Host killed | the resident `dsh web` process was terminated mid-turn |

| Job | stayed `running`: the in-memory turn died with the process while the durable claim and the ordered sequence survived |

**The Control Plane keeps per-connector durable state.** `connectors.last_client_sequence` / `last_server_sequence` together with the `connector_messages` log make the first `connector.hello` a one-time birth: a client that lost its journal is correctly rejected with `CLIENT_SEQUENCE_GAP` / `CLIENT_REPLAY_MISMATCH`. The packaged live runner now takes `--state-dir`, which keeps the connector journal in a caller-owned directory, and `--serve`, which boots a resident host, so a re-run resumes the original journal instead of colliding with the consumed birth. The runner also clears the gauge baseline before booting: `qhb_connector_online` is `bool_or(health = 'fresh')` over **every** connector and a killed connector stays fresh for up to 20 seconds, so a stale sample would otherwise let a rejected birth be reported as a PASS.

With the host tool plugins enabled (`tool-pwsh`, `tool-fs`) the owned attempt's model request carries tools (`edit`, `pwsh`, `read`, `read_image`, `write`) and the job still ends `succeeded`, but the **approval path is not reached**.

The shipped runner was run three times against one connector birth with `--serve`, a persistent `--state-dir` and an isolated `DSH_HOME`:

| Run | Journal | Observed |
|---|---|---|
| 1 | fresh | `gauge-idle`, `boot` (resident `web` template), `connector-online` and `submit` all **PASS**; `connector.hello` client sequence `1` at `2026-09-13T15:27:53.793Z`; the job moved `queued → running` |
| 2 | same `--state-dir` | `connector-online` **PASS** against the cleared baseline; `connector.hello` client sequence `10` at `2026-09-13T15:28:51.730Z` — the connector resumed from `last_client_sequence = 9` with **no** replay mismatch. The job stayed `queued` because run 1's job still held the repository's dispatch slot |
| 3 | fresh (control) | `gauge-idle` PASS, `connector-online` **PARTIAL** and the report **FAIL**: the fresh journal was rejected with `CLIENT_REPLAY_MISMATCH` (server frames `17`–`23`, first at `2026-09-13T15:29:52.656Z`), exactly as the durable-sequence rule requires |
| 4 | same `--state-dir`, after the explicit-home rule | every step PASS except the dispatch-blocked `lifecycle`; `connector.hello` client sequence `15` at `2026-09-13T15:42:14.739Z`, resumed from `last_client_sequence = 14` |

Run 3 is what makes runs 1 and 2 meaningful: the same script, the same connector identity and the same Control Plane return a **PASS** with the reused journal and a **FAIL** without it. The online step can only be recorded PASS while this run's own connector is up, because the runner first waits for the public gauge to clear. `--serve` additionally requires an explicit `--dsh-home`: a resident host shares the home's sessions, storages and credentials with any runtime already using it, so the runner refuses to boot one against the default home (recorded as a FAIL report with `dshHomeSource: default`).

**Finding 3 (fixed in this change).** Instrumenting the installed guard showed `resolved=false` for the live `pwsh` execution: the declared tool set named only `bash`, so the Harness's Windows shell tool was undeclared. The guard's identity check also compared the canonical action name (`git_push`, `write_file`) with the host tool name, which no canonicalised call can satisfy. The tool set now declares `pwsh`, the adapter reports the host tool it resolved (`sourceTool`), and the guard reads that. Verified live: `resolved=true canonical=git_push source=pwsh`.

**Finding 4 (fixed in this change).** Classification then denied every command with `PATH_UNAVAILABLE` and, after that, `UNSUPPORTED_ARGUMENTS`: the executable resolver looked only for the bare name, which never matches on Windows, and once extensions were tried the command identity kept the extension (`git.exe`). The resolver now tries every `PATHEXT` extension and the identity is the basename without it. Verified locally with the packaged build: a live-shaped `pwsh` call running `git push` classifies `approval_required` / `GIT_PUSH`, and `pnpm install left-pad` classifies `approval_required` / `PACKAGE_INSTALL`.

**Finding 5 (partly fixed).** With classification fixed, the live owned attempt requests the approval and blocks on it, but no `approval.requested` reaches the Control Plane. Instrumenting the installed answerer showed why: nothing ever called `registerOwner`, so the trusted-action registry refused every registration and the answerer could not resolve the owned Agent (`owner=false`); and its identity checks read the scoped `ctx.agent` service, which Cordis rejects for a Host-owned Agent context. The composition now takes ownership when the factory publishes the Agent, the registry and the answerer carry the host tool name (`sourceTool`), and the throwing service read is gone: the answerer now finds the owner live (`owner=true`). **Finding 6 (fixed).** The broker then reached its payload validation and stopped: the policy fingerprint was emitted as bare SHA-256 hex while the approval wire schema requires `sha256:<hex>`, so `ApprovalRequestedPayloadSchema.parse` threw and every request degraded to `unavailable`. `fingerprintAction` now returns the protocol form.

**The approval round trip is executed live.** With findings 1–6 fixed, one run recorded:

| Observation | Value |
|---|---|
| Task accepted | `2026-09-13T14:23:48.633Z` |
| `approval.requested` published | client frame recorded by the Control Plane; the job became `waiting_approval` at `14:23:49.214Z` |
| Pending approval seen by MCP | `list_pending_approvals` returned it and `decide_approval` was accepted (`approval.decision` server frame recorded) |
| Decision applied | the connector resumed the turn: the model received the tool result at `2026-09-13T14:23:50.909Z` and continued |

**Finding 7 (open).** After the decision the connector resumes the turn and finishes it. The driver's session stream shows `tool/result`, `step/end`, `assistant/message`, `step/end`, `turn/end` with `kind=completed`, which it recognises as a terminal outcome — but the terminal commit then fails with `TERMINAL_AUTHORITY_UNAVAILABLE` (the authority issuer's re-check of the binding owner, version and operation eligibility). No terminal `job.event` is published, so the Control Plane's job row stays `waiting_approval` even though the work finished.

The mechanism is exact and structural. Issuing a terminal authority performs a live state exchange and `stateEligible` (`terminal-authority.ts`) admits a native outcome only while the Control Plane reports `running`, `cancelling`, or `waiting_approval` **for a failed outcome only**. A successful outcome is therefore impossible while the job sits in `waiting_approval`, and the Control Plane does not return the job to `running` when the decision is delivered (the state machine allows `waiting_approval → running`, but nothing drives it). Completing the approval path needs that resume transition on the Control Plane side — a separate deliverable from this connector change — before a live approved job can reach a terminal state. The Control Plane currently has **no reachable path** out of `waiting_approval`: its only transition to `running` is `dispatched → running` on `job.claim`, and its `statusForEvent` resume branch expects an event the connector's owned-attempt publication guard forbids (an owned `job.event` may only carry `stage.changed`, `progress.updated`, `tool.started` or `tool.finished`, and never a `status` field).

**NOT EXECUTED:** the terminal outcome of an **approved** job, and a live socket-level kill/reconnect cycle. The approval decision round trip itself is executed live (above), and the live restart with ordered continuation is recorded above. The transport-level socket kill, the duplicate-decision rule and the ordered replay of an unacknowledged approval request are exercised over the loopback fixture in CI (`tests/integration/loopback-control-plane.test.ts`); that is transport-level evidence and not a substitute for the live observation. An approved job cannot reach a terminal state until the Control Plane resume transition in finding 7 exists, so this item remains **PENDING** and keeps `v0.2.0` at **NO-GO**.

## Known limitations

- The artifact now carries **no native module**: the durable journal uses the built-in `node:sqlite`, so one build runs on any host the Harness supports.
- The rehearsal runner boots the profile it created from the shipped `headless` template by default: `dsh --profile <name>` with no task exits immediately, and with a task it exits when that task ends, so that mode covers artifact installation, plugin loading, credential-source authentication, Control Plane connection and job claim, but not a terminal outcome. With `--serve` it creates the profile from the shipped `web` template and boots it resident instead, which is the mode the repeatable rehearsal above uses.
- A resident host was verified end to end through a terminal job (`dsh --profile <name> --port 0 --no-open` from a fresh isolated `DSH_HOME`: connector online, offer/claim/sync, `queued → running → succeeded`), and the approval round trip was observed live in the same mode. Only the terminal outcome *after* an approval remains unobservable, for the Control Plane reason in finding 7.
- The live runner keeps its connector journal in a per-run temporary directory by default. Because the Control Plane keeps per-connector durable sequence state, the first live run for a connector consumes its one-time birth; pass `--state-dir <path>` to reuse one journal, which the repeatable rehearsal above exercises, and expect a fresh journal against a consumed birth to **fail** at the online step.
- A macOS host and Keychain were not available, so the Darwin Keychain-default path and every macOS result are recorded as **NOT EXECUTED**; the approved-job terminal outcome and the live socket-level kill/reconnect are recorded as **NOT EXECUTED** for the reasons above.
- The repository has **no root `LICENSE`** and no license metadata in any `package.json` (verified: no SPDX, copyright or license declaration anywhere in the tree). The artifact-side carry of the vendored third-party license texts is implemented and asserted, but choosing the project's own license is the owner's decision, so no license text is invented here.
- The vendored closure adds about 4.5 MiB to the archive (4,699,136 bytes, 598 entries): three pure-JS runtime packages and the retained third-party license text, with no compiled binding.
- `pnpm -r typecheck` could not run on the rehearsal host because the recursive script resolves a store-linked `pnpm` CLI that is missing there (`MODULE_NOT_FOUND`); per-package `tsc --noEmit` was used instead, and CI runs the supported command.
